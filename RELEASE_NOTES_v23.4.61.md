# Team_calculator v23.4.61 — Sprint Storage & Safe Lifecycle

**Исходная версия:** v23.4.60 из пользовательского ZIP-архива GitHub.

## Исправления

1. **Превышение 1 МиБ Firestore.** В `workspaces/main/sprints/{id}` больше не дублируются `input.sprintTaskSnapshots`, `input.sprintTaskActuals`, `input.sprintBaseline.taskSnapshots`, `result.taskSnapshots`. Полное содержимое сохраняется в неизменяемых частях `sprints/{id}/payloadChunks/{revision}_{index}` размером до 80 000 UTF-16 символов; запись частями по 25 документов в batch. Основной документ ссылается на ревизию только после записи всех частей. Проверяется контрольная сумма; при ошибке загрузки спринт не заменяется пустым планом.
2. **Личный текущий план.** Аналогичное версионированное хранение для `users/{uid}/app/main/statePayloadChunks`. Старый вложенный формат читается без миграции и переписывается при следующем успешном сохранении.
3. **Запуск спринта.** Блокировка повторных кликов, резервная копия перед началом, атомарная запись статуса спринта и изменений планирования в `taskPool`. При отказе Firebase сохранение не считается завершённым; восстанавливается состояние планирования и задачи остаются в плане.
4. **Завершение спринта.** Снимки сохраняются по схеме v2, статус и возврат невыполненных задач фиксируются одним атомарным batch. При ошибке — откат локального состояния.
5. **Локальная аварийная копия.** IndexedDB (`teamCalculatorEmergencyDrafts`) хранит изменения плана при ошибках. При следующем входе предлагается восстановить более свежую локальную копию. Если IndexedDB недоступна, запуск/завершение блокируются для предотвращения потери плана.
6. **Восстановление/другие операции.** Ранее сохранённые документы без `payloadRef` продолжают открываться. Список спринтов обновляется только после успешной сборки всех частей; удаление не меняет локальные связи задач до подтверждения Firestore.

## Уточнение по инциденту 10.11.2026 — существующий спринт в «Планировании»

Проблемный спринт уже создан и сохранён: его статус **«Планирование»** корректен, а ошибка возникает именно при нажатии **«Начать спринт»**. Не требуется создавать новый спринт или вручную переносить его задачи.

Обработчик запуска теперь:

1. Проверяет существующий `currentSprintId` и читает его документ с сервера (`getDocFromServer`), убеждаясь, что он по-прежнему в статусе `planning`.
2. **До изменения статуса** переводит существующий документ в раздельное хранение v2 и подтверждает сохранение полного плана, включая текущие локальные правки. ID не меняется.
3. Повторно создаёт аварийную копию, фиксирует исходный план и сохраняет переход `planning → active` вместе с привязками задач в одной Firestore batch-операции.
4. При неудаче возвращает исходное локальное состояние; уже сохранённый серверный план остаётся в `planning`. Если первая запись прошла, а вторая не прошла, безопасная миграция плана сохраняется на сервере.
5. При повторной попытке запуска использует тот же ID; при уже изменившемся серверном статусе останавливается, а не перезаписывает чужие изменения.

Этот сценарий дополнительно проверен в `tests/test_storage.cjs`: сохранённый legacy-спринт, отказ только на втором этапе, неизменность задач и ID, успешная повторная попытка.

## Развёртывание — важно

- **Сначала согласовать и установить правила `firestore.rules`, затем обновить веб-приложение**. Новые пути `payloadChunks` и `statePayloadChunks` требуют отдельного разрешения. Существующие production-правила могут отличаться от файла в исходном репозитории: **сравнить и объединить**, а не без проверки заменить production rules.
- Если в открытой вкладке v23.4.60 есть **повторно составленный, ещё не подтверждённый сервером план**, перед обновлением/закрытием вкладки отдельно зафиксировать список задач и оценки: новая версия не может восстановить данные, уже утраченные старой версией.
- Сделать резервную копию Firestore перед обновлением. Существующие спринты не удаляются и массово не переписываются. При первом сохранении конкретного спринта выполняется ленивое преобразование в v2.
- Очистка старых ревизий best-effort; на одну прежнюю ревизию сохраняется запас. Части новее 5 минут не удаляются, чтобы не нарушить незавершённое сохранение.
- Развёртывание на реальном Firebase из этого ZIP **не выполнялось**. Проверить в тестовом окружении с настроенными Firebase Rules и несколькими пользователями.

## Ограничения

- Атомарное обновление спринта и задач поддерживает максимум 450 записей Firestore за операцию. При превышении сохранение отклоняется без очистки плана. Для сверхкрупных спринтов потребуется отдельная серверная транзакционная оркестрация.
- Если **сам основной компактный документ** превысит безопасный предел 800 000 байт (например, из-за огромного числа идентификаторов или ролей), сохранение блокируется с сообщением, а локальная копия сохраняется.
- После обрыва соединения до подтверждения записи могут оставаться неиспользуемые части новой ревизии; приложение очищает устаревшие части при последующих сохранениях.

## Проверки

`node tests/test_storage.cjs`

Автоматические тесты с имитацией Firestore проверяют: данные больше 1 МиБ, сборку частей и Unicode, повреждение/пропуск части, атомарный отказ записи при запуске, отказ при завершении, восстановление статуса и сохранение текущего состояния пользователя. **Реальная интеграция с Firebase и браузерный UI не тестировались.**

### Ручной smoke-test перед production

1. Создать тестовый спринт с большой историей снимков задач (> 1 МиБ в старом формате), дождаться автосохранения, обновить страницу — все задачи и оценки должны сохраниться.
2. Нажать «Начать спринт» и проверить статус/исходный план/привязки taskPool; при имитации отказа Firestore статус должен остаться «Планирование», список задач — прежним.
3. Завершить спринт с незавершёнными задачами: история/факт сохранены, незавершённые возвращены в пул. При отказе записи откат статуса и привязок.
4. Проверить создание копии, открытие старых спринтов, права владельца/админа/читателя, совместную работу и ссылки с `?sprint=`.
5. Проверить восстановление IndexedDB после отключения сети и обновления страницы. На тестовом профиле проверить, что подтверждённое сохранение не вызывает ошибочного восстановления.

# Team_calculator v23.4.62 — внеплановые задачи (release candidate)

База: предоставленный архив Team_calculator-main.zip, v23.4.61, GitHub commit `b7f74f79a2a244335d0ba707b8fd1f345dbae23b`. Старые функции, конфигурация Firebase, GitLab-эндпоинты, хранение v2 и аварийное восстановление сохранены. Исходный ZIP не изменялся. В комплект поставки включён обновлённый Mac-коннектор v1.4.27 на базе предоставленного v1.4.26. Промышленный E2E ещё не выполнен.

## Поведение

- Начало спринта — существующее действие «Начать спринт», фиксирующее `sprintBaseline.selectedTaskIds`. Не календарная дата GitLab Iteration. Признак не хранится в общем пуле: для активного/завершённого спринта он вычисляется как участие в спринте без участия в исходном плане. Для старых спринтов без исходного плана признак неизвестен, а не «внеплановая».
- Задача, добавленная через Team Calculator после запуска, отмечается «Внеплановая · unexpected», оранжевая полоса и бейдж. Фильтр «Состав спринта»: все, плановые, внеплановые; работает совместно с прежними фильтрами и сбрасывается общей кнопкой.
- Сводка: количество внеплановых задач в текущем составе и всего, план и факт в человеко-днях. Для активного спринта план по текущему составу; после завершения — по всем участникам, в соответствии с v23.4.61. Принятый факт перенесённых задач сохраняется.
- При включении внеплановой задачи со ссылкой на GitLab сначала подтверждается сохранение спринта, затем в существующей очереди создаётся запрос назначения Iteration с дополнительным указанием `unexpected`. Для плановой задачи, задачи без URL, обычного обновления метаданных и возврата в пул лейбл не отправляется. Задачи, добавленные только в GitLab, не отслеживаются.
- Повторная отправка доступна для внеплановой задачи активного редактируемого спринта, если лейбл не подтверждён метаданными GitLab. Повторное добавление лейбла должно быть идемпотентным. Интерфейс не выдаёт факт создания задания за подтверждение GitLab. У существующих активных спринтов задачи выделяются по baseline, автоматически массово не маркируются; доступна явная отправка по отдельной задаче.
- Решение до отдельного согласования: лейбл `unexpected` в GitLab автоматически не снимается при переносе или возврате; в Team Calculator классификация определяется для каждого спринта независимо. Задача из исходного плана, возвращённая в тот же спринт, остаётся плановой. Другие GitLab labels не должны изменяться.

## Контракт GitLab-коннектора v1.4.27

Коннектор получен отдельно от веб-приложения и обновлён до v1.4.27. Его необходимо установить на Mac и выполнить промышленную проверку. Уже существующая очередная операция `sync_gitlab_issue_metadata` получает дополнительное поле, например:

```json
{
  "type": "sync_gitlab_issue_metadata",
  "sprintId": "<saved-sprint-id>",
  "sprintLifecycleStatus": "active",
  "tasks": [
    {"taskId": "<task-id>", "title": "<title>", "externalTaskUrl": "<issue-url>"}
  ],
  "iterationMutation": {
    "mode": "set",
    "iterationId": 123,
    "iterationTitle": "Sprint",
    "addLabels": ["unexpected"]
  }
}
```

Остальные поля очереди и тип задания остаются прежними. В коннекторе реализовано:

1. Сохранить старую обработку задания без `addLabels`. Разрешить только точное значение `["unexpected"]`, только одну задачу, только `mode: set` и активный спринт. Не использовать произвольные имена лейблов из очереди.
2. Перед выполнением проверить актуальное состояние привязки и исходного плана в Firestore; не исполнять устаревший запрос после переноса или удаления задачи. Использовать только существующую авторизацию и проверку корпоративного GitLab URL.
3. Проверить существование лейбла `unexpected` в проекте или унаследованных доступных лейблах; при отсутствии сообщить ошибку, не создавать новый лейбл. Добавить его аддитивно через GitLab Issue API `add_labels`, не заменяя список `labels`. Если он уже присутствует, не выполнять лишнюю запись.
4. Сохранить существующую обработку назначения Iteration. После изменения обновить метаданные issue (`gitlab.labels` в taskPool), проверить наличие `unexpected` и записать фактический результат в существующий статус задания. Ошибка лейбла не должна сообщаться как успешное завершение задания. Повторное выполнение безопасно и не меняет оценки, assignee или другие labels.

Старый коннектор может проигнорировать поле `addLabels`; интерфейс в таком случае не подтвердит наличие лейбла. В комплекте предоставлен обновлённый `metadata_connector.py`, совместимый с этим контрактом. Cloudflare Worker в текущей реализации фронтенда не требуется менять: очередь создаётся напрямую в Firestore.

## Firestore Rules

Поставляемые с v23.4.61 правила разрешали создание очереди только интеграционному пользователю, хотя браузер уже создаёт задания напрямую. В файл добавлено узкое разрешение для нового запроса: активный пользователь, владелец спринта или администратор; сохранённый активный спринт; задача состоит в текущем составе, не в baseline и не в возвращённых; URL и привязка сверяются с taskPool, Iteration — с сохранённым спринтом. Разрешён только `addLabels: ["unexpected"]`. Остальные разрешения не изменены. **Сравнить с действующими production rules и объединить, не заменять вслепую.** Правила не проверены в эмуляторе Firebase и требуют проверки перед выкладкой.
